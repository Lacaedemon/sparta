## 2024-07-22 - Optimize high-frequency loop distance calculations
**Learning:** In GDScript, `distance_to` computes an expensive square root. In high-frequency loops, such as per-soldier combat resolution in `SoldierMelee.gd` against all defending soldiers in an engaged block, using `distance_squared_to` and comparing it to the squared threshold distance significantly avoids compute overhead without breaking readability.
**Action:** Always prefer `distance_squared_to` over `distance_to` when evaluating thresholds (e.g. reach, range, contact) inside O(N^2) loops or hot paths like targeting and spatial queries.
## 2024-11-20 - Ensure zip files and .import changes don't get committed
**Learning:** When downloading headless Godot to run tests, Godot updates auto-generated `.import` files. Those changes, and the Godot zip file/executable, must not be committed.
**Action:** Always clean up downloaded tools and revert `.import` files modified by the headless engine run before committing.
## 2024-11-20 - Precompute loop invariants
**Learning:** Even trivial math like squaring a constant (`RANGED_RANGE * RANGED_RANGE`) should be precomputed before entering a high-frequency loop to squeeze out maximum performance and address review feedback about repeated recomputation.
**Action:** Always extract invariant math operations (like threshold squares) out of `for` and `while` loops.

## 2026-07-25 - Optimize high-frequency loop distance calculations in Unit AI
**Learning:** In GDScript, `distance_to` computes an expensive square root. In high-frequency O(N) loops like `Unit._think` or `Unit._support_tick` that run every frame for every unit, evaluating thresholds using `distance_squared_to` against a squared threshold is a low-risk, high-impact optimization that avoids the `sqrt` compute overhead.
**Action:** Always prefer `distance_squared_to` over `distance_to` when evaluating threshold ranges (e.g. `RANGED_RANGE`, `attack_range + RADIUS`, `SKIRMISH_KITE_DISTANCE`) in unit AI update loops.
## 2026-07-28 - Optimize minimum distance loop variables
**Learning:** When replacing `distance_to` with `distance_squared_to` inside loops that find the minimum distance, ensure the tracking variable (e.g., `nearest_dist`) is appropriately renamed to `nearest_dist_sq` and stores squared values for correct comparisons and maintainability.
**Action:** Always rename distance tracking variables to indicate they store squared values when applying the `distance_squared_to` optimization to prevent logical bugs later in the function.
## 2026-07-29 - Syntax errors and short-circuit hazards in distance checks
**Learning:** In GDScript, placing a comment (`#`) inside a line-continuation block (connected by `\`) breaks the parser, causing fatal syntax errors. Separately, duplicating a complex threshold expression to square it (e.g. `(a() + b()) * (a() + b())`) evaluates the function calls twice, giving back the compute the `sqrt()` removal saved.
**Action:** Place comments outside line-continuation blocks. When a threshold involves function calls, compute it once into a local and square the local -- **but only when the original expression was not relying on short-circuit evaluation to guard its operands.** Hoisting a threshold out of `is_instance_valid(x) and ... x.foo()` evaluates `x.foo()` unconditionally and crashes on a freed instance; in that case keep the computation inside the guarded branch instead. This was a real, shipped crash in `Order.gd`'s `resolve_friendly_target`, one line above the `is_instance_valid` check that exists to catch exactly that state.
## 2026-07-30 - A performance PR proves itself with a work graph and a clip, not a claim
**Learning:** A backend-only optimization is the one kind of change a reviewer can neither read off the diff nor see in a clip, and wall-clock evidence does not close the gap: the CI benchmark's own baseline documents a ~20-30% run-to-run swing between functionally identical builds, wide enough to hide a real win or manufacture a fake one. Deterministic work COUNTS do close it -- `scripts/SimOps.gd` tallies the sim's dominant work units per tick, and the same scenario and seed give byte-identical counts on any machine, so a before/after graph differs only where the code changed.
**Action:** On every performance PR, run `tools/perf/ops-before-after.sh`, commit the resulting `demos/shots/*.png`, and embed it plus the per-bucket table it prints in the PR description -- AND record a real demo clip (`demos/demo.<slug>.json`, never `"skip": true`) on the optimized build, since "it only changed how fast" is the claim under review. If the two lines coincide exactly, say so and explain why (an uncounted path, or a cheaper-per-operation change like `distance_to` -> `distance_squared_to` in a loop no bucket covers) instead of presenting a flat graph as a win. When adding a counter, place it at PASS granularity -- tally into a local integer (or derive the count from the loop bounds) and report once per pass; never call into `SimOps` from an inner loop or a per-soldier function, which measured a real ~2% cost on every tick before the counts were hoisted.
## 2024-07-28 - Optimize length() with length_squared() in threshold comparisons
**Learning:** In GDScript, comparing vector lengths with `Vector2.length()` triggers an expensive mathematical square root operation. We can bypass this computation by using `Vector2.length_squared()` instead, comparing the result against a squared threshold (e.g. comparing `move_vec.length_squared()` against `0.01 * 0.01` instead of comparing `move_vec.length()` against `0.01`).
**Action:** When comparing the magnitude of a vector to a threshold distance or for zero-checks, prefer `length_squared()` over `length()` and square the threshold appropriately, especially in high-frequency loops or maneuver logic.
